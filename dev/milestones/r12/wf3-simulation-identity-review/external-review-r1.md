## Findings

### ext1-1 [major]
- section: §7.5 Return-level estimator precondition; §12.1 GF-15
- finding: The proposed GEV benchmark fixes the distribution’s location and scale while judging relative quantile error, then uses that benchmark to qualify a screening policy expressed only through block count and return period. Relative quantile error depends on the location-to-scale ratio as well as shape and sample size. The bounded scope is acknowledged, but the proposed criterion does not establish which discharge regimes its numerical tolerances represent, particularly for low-flow levels near zero.
- rationale: For a location-scale distribution, write the true quantile as \(q_T=\mu+\sigma z_T\). A standardized estimation error \(\epsilon\) produces relative error \(\sigma\epsilon/|q_T|\). Changing location can therefore change the benchmark’s pass/fail outcome without improving the fitted tail or increasing sample information. A policy passing the chosen distribution cells can have substantially different relative errors for low-flow distributions with another location-to-scale ratio. Calling the screening values scientifically validated, even with a matrix qualification, risks conflating a particular estimator benchmark with evidence supporting the operational screening rule.
- suggested_fix: Distinguish validation of the estimator benchmark from validation of the screening policy. Add a location-invariant error measure, such as error normalized by the generating scale, and explicitly justify the location-to-scale ratios used for relative-error criteria. Include near-zero low-flow cases or define them as outside the validated domain, with that limitation persisted in metric-set metadata. Retain the unchanged estimator and provisional screening values until the revised criteria are reviewed and executed.

### ext1-2 [major]
- section: §5.4 Collection location and files; §6.3 Simulator adapter boundary; §6.4 Forcing compatibility and refusal; §9.1 Workflow identities and rule ownership
- finding: The durable handoff does not explicitly carry all inputs required by the existing forcing-preparation path. In the directly cited `run_stress_test.smk` at the declared code baseline, preparation receives `DATA_SOURCES`, `clim_source`, and an `oro_path` pointing to the historical climate store’s `orography.nc`; the accompanying comment identifies the CHIRPS/CHIRPS-global branch as requiring this sidecar. The proposed `RunForcing` record, collection artifact contract, and simulation-input inventory do not specify how that ancillary data and preparation context survive independent collection consumption.
- rationale: A valid generated forcing file and a ready Wflow model do not themselves establish availability of the source-grid orography and catalog context used by the current preparation operation. A consumer can pass the proposed collection checks yet fail when preparing that supported forcing branch after the original store is unavailable. Recovering those inputs implicitly from the current project environment would instead introduce a hidden result-affecting dependency outside the stated handoff and fingerprint contracts.
- suggested_fix: Inventory the existing preparation inputs and assign each an explicit owner. Persist required source-grid ancillary artifacts with the collection, or declare them as separately inventoried simulation inputs whose content digests enter simulation identity. Carry the necessary physical preparation metadata through the neutral forcing contract without exposing stochastic scenario fields. Add a CHIRPS-path acceptance fixture that prepares forcing after the original generation store is unavailable and compares the prepared result with the existing path.

### ext1-3 [major]
- section: §4.1 Workflow and target boundaries; §5.2 Parse-time enumeration; §8.4 Metric-set identity and provenance; §9.5 Runner ordering and modes
- finding: The specification leaves unresolved how fresh invocations schedule artifacts whose directory identities depend on outputs produced during that invocation. `metric_set_id` requires the response-inventory digest and resolved Class-C reference provenance, which are unavailable before a fresh simulation finishes. Similarly, the runner resolves `collection_id` before invoking generation, although §9.1 permits generation-owned preparation of the historical climate inputs whose byte digests enter that identity. Conditional inclusion of Wflow rules does not resolve either scheduling dependency.
- rationale: A conventional parse-time target expansion cannot name these final content-derived paths from inputs that do not yet exist. Implementers must introduce an additional planning boundary, a supported checkpoint, or a stable completion target with runtime publication semantics. Without a specified choice, fresh execution can require an undocumented second invocation or accidentally depend on retained artifacts. The existing feasibility gates do not explicitly require exercising both identity-resolution cases with their determining inputs absent.
- suggested_fix: Specify the scheduling mechanism separately for source preparation and metric publication. For example, complete source preparation before resolving collection intent, and use a supported response-completion checkpoint or a stable metric-operation receipt that identifies the runtime-published metric set. Preserve the content-derived identities. Extend feasibility gates to start without the historical extraction and without responses, then require one documented invocation to produce and identify the correct collection and metric-set directories.

### ext1-4 [major]
- section: §7.4 Metric-unit index and result tables; §9.2 Normative seam-contract replacements; §12.1 GF-10
- finding: The result validators establish unit membership, grain, vocabulary, and design coverage, but do not explicitly require uniqueness and exact coverage of the expected `(metric, location, unit_id)` result keys. A complete unit index is not evidence that every selected metric was emitted for every applicable unit and location.
- rationale: A writer could omit one return-level metric at one gauge and design point while another metric preserves that design point’s coverage. Every remaining row could satisfy the listed invariants, and the complete index would still pass. Duplicate result keys could likewise survive the stated checks and receive unintended weight in downstream aggregation. GF-9 would detect omissions during the one-off migration comparison, but it does not protect later metrics-only recomputation or newly selected metric sets.
- suggested_fix: Derive an expected result-key set independently from the selected declarations, declared grains, bundle memberships, and required locations. Require emitted keys to be unique and exactly equal that set before publishing `metrics.json`; separately enforce each metric’s value-validity policy. Add negative fixtures that remove one metric-location-unit row and duplicate another while retaining a complete unit index and overall design coverage.
