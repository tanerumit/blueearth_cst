## Context and objective

WF1 produces a rapid automated Wflow assessment from global inputs. An expert needs to inspect a poor result, change the model, run another historical evaluation, compare evidence, and repeat. Today the only model is mutable: editing it can invalidate the evaluation beside it and make an existing WF4 experiment impossible to rerun. A config snapshot does not identify the bytes changed by hand.

Introduce named, complete model revisions with explicit parentage. An expert works in a private copy, optionally applies HydroMT recipes, makes direct edits, and explicitly seals the result. Evaluation and selection follow sealing. Every sealed revision and evaluation remains attributable; a later WF1 build or expert edit cannot silently replace it.

The unattended WF1 path remains the default. Revision mode adds an explicit boundary between invocations; no Snakemake process waits for a human editor. This is expert model development, not automatic calibration. Better historical metrics are evidence about fit under a stated evaluation protocol, not proof of calibration, predictive validity, or climate robustness.

Non-goals: parameter optimization; a new hydrological model API; changing HydroMT internals; changing WF3; selecting forcing from climate projections; automatic ranking of revisions; a separate model copy for every WF4 experiment; portable redistribution of all upstream build datasets.

## Current behavior and constraints

- `build_model.smk` writes `models/hydrology/wflow`. Its HydroMT writer chain ends with `add_climate_forcing`, which owns `.model_final`. Model readers wait on `ancient(.model_final)`. This is an ordering edge, not a content seal. `write_gauge_index` subsequently writes a derived geometry index; historical execution, exports, evaluation and metadata also write under the root.
- [ADR 0004](../../../decisions/0004-order-model-readers-on-a-terminal-sentinel.md) documents the whole-root HydroMT rewrite hazard and Snakemake's deletion of failed jobs' declared outputs. A reader waiting only on `.outputs_configured` can overlap the last writer.
- `run_historical_simulation` runs the model TOML directly; raw `run_default/output.csv` is `temp()`. Retained tables and evaluation metrics survive, but raw precision cannot be assumed recoverable from them. The baseline gate needs `--notemp` today.
- `model_digest.py` version 1 hashes TOML and lexical, pointer-derived paths, including explicit absence markers. It intentionally does not inventory every geometry, recipe or build log. It also discovers output-shaped keys without classifying them as required inputs. Digest agreement does not prove required inputs exist, nor that the model is valid.
- `copy_config_files.py` retains the latest WF1 run record. Its configuration hashes omit scientific dataset identity. [ADR 0011](../../../decisions/0011-preserve-config-sources-with-run-records.md) supplies the accepted direction for exact-source archives; its accepted design and the current implementation must not be conflated.
- WF4's `simulate_and_metrics.smk` hardcodes the same model root in fingerprinting, forcing preparation, simulation-intent construction, grid sizing and resource estimation. `simulation_record.py` also validates a closed five-field model-reference schema. Updating the first path assignment alone is insufficient.
- Existing WF4 references are immutable. Their path is part of retained attribution, while simulation identity v2 uses the runtime digest, simulator/environment, preparation and response contract. Rewriting an old reference to match today's model would defeat the drift guard.

## Normative revision contract

### 4.1 Storage and ownership

Use these project-relative homes:

```text
models/hydrology/wflow/                         existing automated WF1 root
models/hydrology/wflow-drafts/<draft_id>/        editable attempt, never selectable
models/hydrology/wflow-revisions/<revision_id>/
    model/                                     complete runnable model inputs
    revision.json                              immutable seal and inventories
    provenance/                                exact sources, operations, input records
models/hydrology/wflow-evaluations/<revision_id>/<evaluation_id>/
    request.json                               frozen evaluation request
    result.json                                completed inventory and outcome
    run/                                       effective TOML, native responses, logs
    results/                                   tables, metrics, plots, assessment
```

Names are unique lowercase portable identifiers; reject separators, traversal, Windows reserved names and case-fold collisions. Names are labels, not hashes. No rename or replacement of a published revision is supported. Different revision labels may legitimately have identical runtime digests.

`model/` holds every file needed to run the model and retain it as an updateable HydroMT model, including forcing, input states where applicable, tables and geometries. Recipes, catalog snapshots and notes belong in `provenance/`. Published evaluation artifacts are never children of `model/`.

No hardlinks, symlinks or junctions may couple a draft, parent or sealed model; reject them or materialize independent regular files before sealing. Reject case-colliding paths and paths escaping the model. Required runtime inputs must exist. Optional input absence is accepted only where the chosen Wflow configuration permits it. Output paths are checked separately and must not overwrite model inputs. All model data necessary for execution is copied; external build datasets may remain external only with their identities and retrieval limitations explicitly recorded. Seal validation must reconcile actual engine input resolution with the v1 pointer inventory, including `dir_input` and path modifiers. A configuration whose inputs the existing digest does not cover is unsupported in revision mode until a separately versioned digest change is designed; it cannot pass merely because a full-tree hash exists.

### 4.2 Parentage and editing

A root revision is an explicit import of a quiescent automated model. It has `parent: null`, an import source path and inventory, and provenance completeness `observed_snapshot` unless an intact build record and input evidence support stronger claims. Import does not assert how unknown historic bytes were produced. It copies the WF1 configuration evidence then, before another WF1 invocation can replace it.

Each expert child has exactly one sealed parent, recorded by revision ID and full seal hash. Cycles and changing the parent after draft creation are forbidden. Copy the complete parent's `model/` into the draft and record the parent's verified inventory. Preserve additions and ancillary files that HydroMT might not reproduce. Recipe updates operate only on the draft; never run an in-place HydroMT update on a sealed parent.

Both routes may occur in one draft:

1. **Recipe operation:** capture recipe and custom catalog bytes before execution, resolve and record consumed data identities, record exact command, code/environment, attempt outcome and pre/post file inventories. Use the installed plugin's native update surface. The vendored update guide documents `hydromt update wflow_sbm <input> -o <output> -i <recipe> -d <catalog>` and warns that updates otherwise overwrite their input and normally write all components. The implementation must verify behavior for the pinned plugin; partial component writes must also persist changed configuration.
2. **Direct edit operation:** the expert edits regular files in the draft and records purpose, author and method. At seal, inventory every file and compare it with the parent and most recent recorded operation. Retain additions, deletions and before/after hashes; keep text diffs where meaningful. The complete resulting bytes, including binary NetCDF edits, are authoritative. An edit without a regeneration script is labeled `snapshot_reproducible`, not `recipe_replayable`; it can still be sealed and evaluated.

Operation records never claim to reconstruct the order of unobserved manual edits. A final inventory catches unrecorded changes; the seal requires explicit acknowledgement and a description of their purpose. Blank provenance is rejected; an honest manual operation is accepted. A no-change child is permitted with a stated reason and equal runtime identity.

### 4.3 Identities and seal contents

Keep three independent identities:

| Identity | Hash material | Meaning |
|---|---|---|
| Runtime model digest | Existing `model_digest.py` v1 entries and algorithm | Same recorded Wflow runtime-input state under that algorithm; not full provenance or scientific validity |
| Revision seal hash | Versioned canonical revision record, parent seal, full `model/` file inventory, provenance inventory and operation record digests | Exact attributed revision, including changes outside runtime pointers |
| Evaluation ID | Versioned canonical evaluation request: revision seal, runtime digest, evaluation protocol, data identities, engine/environment and adapter/analysis code inventories | One attributable evaluation request; result bytes are separately inventoried |

Inventories contain normalized root-relative POSIX paths, byte size and SHA-256, sorted by path. Hash file bytes without newline rewriting. Canonical records use the repository's existing canonical JSON facility with an explicit schema identifier; exclude the record's own hash field and derived convenience locations. Revision timestamps and author notes are immutable provenance and may distinguish seals; they never alter the legacy runtime digest. Do not use directory mtimes as evidence.

The seal contains schema version, revision ID, parent link, import origin if any, runtime digest version and entries, full inventories, operation provenance, creation/seal actor and times, toolbox code identity, environment locks, and structural validation result. File inventories cover all stored regular files; there is no broad unrecorded exclusion of log or unknown filenames. Housekeeping markers and prior run outputs are moved out of `model/` during preparation only after verifying they are not required inputs. Ambiguous files are retained and inventoried, or preparation stops for classification.

An import records exactly which source files were excluded as generated execution products. It does not delete or rewrite them in the original WF1 root. A change required for relocation, such as replacing an absolute in-root path with a relative path, is an explicit operation; it can change the runtime digest and must not be represented as byte-identical import.

## Workflow and publication boundaries

### 5.1 Operations between invocations

Expose explicit prepare/import, recipe update, seal, evaluate, compare and export operations through a user-facing wrapper in `scripts/`, backed by shipped modules. Final CLI spelling is an implementation detail. Every operation records an invocation and exits; an expert can inspect and edit between invocations.

Revision lifecycle is `draft → sealed`; discarded/failed drafts stay unselectable. Evaluations have independent attempt states. Selection does not modify either object. To change a sealed model, prepare a child. To change the evaluation protocol or observations, make a new evaluation request for the same revision.

Prepare verifies the parent, acquires exclusive draft ownership, copies independently and verifies the copy. Seal requires that the editor and all writers are stopped, rechecks the parent link, validates paths and model structure, captures edits, and copies into private publication staging. Hash the staged snapshot and check the source still agrees; reject a moving draft. Readers consume only the staged snapshot that was validated, never the concurrently editable directory.

Publish the completed revision directory once using an atomic no-replace operation on the same filesystem. The seal is part of that publication, not a marker written into a partially visible final tree. An existing name with identical seal is an idempotent success; any other existing content is a conflict. Filesystem read-only attributes are advisory: verify hashes before use. Publication integrity depends on the root's supported atomic primitives; unsupported network shares fail clearly.

### 5.2 Snakemake ordering and output deletion

Keep existing WF1 `.model_final` ownership and reader ordering. The import operation must wait for the **complete requested WF1 invocation**, including gauge index and retained evaluation outputs, not merely for `.model_final`. The terminal marker only means the main HydroMT mutator chain finished. A model-root writer lock prevents import and WF1 rerun overlap across processes; all supported WF1 wrappers acquire it before writes. Raw Snakemake launch into a revision-enabled root must either acquire the same lock in its entry guard or fail with wrapper guidance, before parse-time archive writes as well as scheduled model writes.

Within recipe execution, no validator, inventory scan, plot or engine reader starts before the final recipe writer exits. If multiple recipes run, their explicit sequence and completion edges establish order. Do not infer ordering from a model file declared by an earlier rule.

Evaluation rules consume a sealed revision and frozen request. No rule has the sealed model directory as `output:`. Rules write attempt-private outputs; the wrapper validates and publishes completed evaluation inventories after Snakemake success. Final revision and evaluation objects are outside Snakemake's deletion ownership. A forced rule or failed job must never delete a published object. A temporary guard sentinel is valid only within the invocation; preflight revalidates on every invocation, including no-op runs.

Existing legacy `temp(output.csv)` stays unchanged. Revision evaluations retain the native responses needed to recompute metrics at their original precision; at minimum the historical native CSV, effective run TOML and Wflow log. Intermediate copies and forcing caches may be temporary, but no retained evidence or sealed model file may be `temp()`. If a requested output contract needs another native response, declare and retain it before execution.

### 5.3 Root authority and concurrency

This design launches no run, declares no project root managed and holds no namespace claim. Actual root status is unknown at design time. Local revision locks and an atomic directory publication do **not** establish CST run-control conformance.

At execution, first inspect the project owner's managed-root declaration. Under a managed root, the operation must use the existing conforming adapter: validated immutable intent, ten capability bindings, typed stage graph, config/design/intent digests, atomic namespace claim excluding overlapping roots, and a fenced writer before `ready`. Resumable operations require `managed` conformance with typed CPU/memory/scratch/output resource claims, attempt-private staging, sealed objects and token-checked inventory publication. The paths above then become materialized inventory views. If no adapter implements this, refuse execution there rather than invent a parallel partial contract. A legacy import into such a root follows the `provenance` profile and its nonresumable lifecycle.

For an ordinary, undeclared root, wrapper locks and no-replace publication supply this feature's local safety only; report that CST conformance is not declared, never serialize an invented third conformance level. Root declaration or general run-control adoption is outside this feature. No completed modeling stage is integrated while its validation handoff is pending.

## Evaluation and WF4 selection

### 6.1 Historical evaluation

An evaluation request freezes the revision seal and runtime digest; forcing bytes and period; spin-up exclusion; initial-state policy; observation bytes, station mapping and quality/missing-data treatment; units/calendar/timestep alignment; output variables; metrics and calculation code; engine, environment and execution settings. A retained request and successful engine exit alone do not certify acceptable model performance.

Execute Wflow against an evaluation-private **full working copy** of the sealed model in v1. This costs disk but gives the existing relative-path model a clear writable boundary. Generate and retain a run TOML whose allowed changes are execution destinations and the explicitly requested historical time/output protocol. Record its exact digest and a classified diff against the sealed TOML. A physics/input change outside the request is an error requiring a child revision. Verify the sealed model before and after execution; copying does not authorize a writer on the source.

Reuse WF1's exports and evaluation routines after separating their model-input root from evaluation-output root. `plot_results.py` currently derives its evaluation folder from `model_dir`; the refactor must pass distinct roots and remove hidden writes to the sealed model. Native responses, table exports, metrics, figures, warnings and validation evidence are published together with checksums only after required products are complete. The disposable execution copy is removed only after publication and inventory verification; failed attempt copies remain available for diagnosis under the explicit cleanup policy.

Model-validator supplies a versioned assessment with three distinguishable verdicts: structural/runtime validity, evidence adequacy, and fitness for the named assessment purpose. Structural checks cover required input existence, spatial grid/CRS, forcing units and chronology, state configuration, gauge identity and output completeness. Scientific checks examine hydrographs, water balance and available performance metrics, seasonality, high/low flows where the observations support them, and warning diagnostics. Numerical acceptance thresholds and evaluation periods are specified by the assessment owner and model-validator before comparison; no universal KGE/NSE cutoff is introduced here.

Comparison exports one row per revision × evaluation × station × metric, retaining sample count, period, masks and reference IDs, plus links to hydrographs and the assessment. A comparison-protocol hash groups evaluations with matching forcing, observations, mapping, alignment, period, metric definitions and evaluation settings. Changing forcing or station support creates a different comparison group: show the evaluations separately or label the comparison exploratory, never report an unqualified improvement. Model changes in mapping/domain require explicit common-support assessment. Missing observations yield `insufficient_evidence`, not an invented fit score.

Record whether observations were used to guide edits. Repeatedly choosing improvements on the same record makes it development evidence; a held-out period/site is needed to make an independent validation claim. Users may select a structurally valid revision with limited observational evidence for a first-order assessment, but must retain that limitation and a rationale. Fatal structural/runtime failure cannot be waived into a valid selection. The feature neither optimizes nor automatically recommends a winner.

### 6.2 Selection and experiment binding

Add optional `model_revision`, `model_evaluation` and `model_selection_reason` fields to the **simulate_system workflow configuration**, since these control WF4 selection. For a new experiment, omitted/null `model_revision` means the legacy automated root and the two accompanying fields must be absent. An explicit revision ID resolves under `wflow-revisions/<id>/model`; arbitrary external paths and `latest` aliases are rejected. `model_evaluation` must name a complete evaluation of that exact seal, with an accepted structural/runtime verdict; `model_selection_reason` must be nonempty and acknowledge retained evidence limitations. No second mutable selection registry is introduced. Freeze all three in the new experiment's creator archive/binding. The user changes the source workflow config to select a revision for future experiments.

Resolve the model exactly once in the owned WF4 wrapper and pass the verified result to the workflow. Every downstream consumer uses it: fingerprint and drift checks, simulation-intent preparation, grid/downscaling paths, resource probes, simulator input references and path-token logging. Search both `*.smk` and shipped Python/Julia modules for path reconstruction; closed config schemas and `cross_workflow_inputs` validation must recognize the new boundary.

For a **new** experiment, freeze revision ID, seal hash, evaluation ID and selection rationale along with the existing five-field runtime reference. Introduce a versioned revision-binding document, referenced and hashed by a successor simulation-intent schema for revision-mode experiments; do not append unrecognized fields to simulation/v2's closed reference schema. Keep runtime digest algorithm v1 unchanged. Scientific simulation identity continues using runtime digest plus the existing simulator/forcing/response ingredients, so a note or geometry-only revision does not claim different physics. Attribution still distinguishes the seals, and changing revision labels never retargets an existing experiment or authorizes cross-experiment output reuse.

For an **existing** experiment, its retained binding and model path are authoritative before resolving current defaults. An omitted/null selector means resume that binding; explicit selection fields that disagree with retained values fail before preparation. A changed project preference therefore cannot redirect an old experiment. Legacy simulation/v2 reads retain their exact schema and digests. A legacy reference to the automated root still checks that root and fails if its runtime inputs changed; importing identical bytes elsewhere does not silently rewrite its path.

Metrics-only operations may continue using complete retained native responses under the existing WF4 metric contract when the source model is unavailable; they must not create new simulations or claim live-model verification. Operations that prepare, resume or regenerate simulations require the referenced model and integrity checks even when most outputs exist. Export of historical retained evidence reports current verification status and can preserve a drifted object's old evidence without presenting it as rerunnable.

## Integrity, drift, and recovery

Before parent copy, seal, evaluation, WF4 simulation or verified export, check record hashes, full model/provenance inventory and runtime digest, and report changed, missing and added paths. A provenance-only change invalidates the revision seal even if the runtime digest agrees. Existing legacy experiments retain their narrower runtime guard. Verify selected evaluation result inventories and their revision link as well.

Published objects are immutable by contract. On drift, refuse computation and selection; retain the original manifest and old evaluation evidence. Recovery is either restoration of exact recorded bytes from a verified backup, or capture of altered bytes into a new draft with `recovered_from` provenance and a new revision. Do not “repair” the old seal, rewrite an old evaluation request or refresh an experiment's reference. A corrupted original parent cannot be used as a verified copy source; the recovery import explicitly records that distinction.

An interrupted recipe leaves an unsealed failed draft attempt. Preserve its logs and partial files for diagnosis, then retry from the verified parent or a recorded complete operation checkpoint. Do not presume an interrupted in-place HydroMT update is idempotent. An interrupted evaluation leaves attempt staging, not a completed evaluation. Reuse requires equal request identity and verified completed prerequisites; otherwise make a fresh attempt. A successful rerun of the same request that yields different native bytes is investigated as nondeterminism, never silently replaces the published result.

A publication crash may leave an unreferenced staged object. Reconcile against a verified seal and publication ownership; quarantine incomplete objects. Never overwrite a published name on retry. After process death, a lock is released/recovered only after establishing that the writer is no longer active; age alone does not permit a takeover. Managed roots additionally require legal CST run-control transitions and fresh fencing tokens. No automatic garbage collection or deletion of revisions with dependent experiments is in scope.

Export produces a new inventory-covered bundle of the selected revision, chosen evaluations and selection/lineage records. Include parent seals even when parent model directories are omitted, and state that omission. Verify the bundle after copying; state whether it supports exact simulation rerun, direct-edit snapshot recovery, and/or full recipe rebuild. A full directory is not proof that external source datasets and software remain obtainable.

## Compatibility and migration

1. With no revision selector, WF1 paths, default targets, numerical outputs, temporary policy and current-only archive behavior stay as today. WF4 new legacy-mode experiments retain simulation/v2. Add wrapper concurrency guards without forcing model rebuilds.
2. Opt-in starts with a completed, quiescent WF1 root. Import its complete model inputs and contemporaneous provenance as the first sealed revision. Leave the original model and evaluations untouched. Historical pre-import outputs may be exported as legacy evidence with explicit attribution limits; they are not relabeled as a newly verified revision evaluation. Run the new evaluation operation to establish the revision's evidence.
3. Expert children preserve full parentage and rerun evaluation. Adding a revision does not modify `build_model.smk`'s target root or install symlinks at its legacy location.
4. A subsequent WF1 rerun updates only the automated root and its latest records. It does not alter sealed revisions or existing revision-mode experiments. Capturing that new automatic build is a new root import, with a build/import relationship recorded rather than false derivation from an expert child. Legacy experiments remain protected by their existing drift failures.
5. Do not migrate old experiment references in place. To simulate an old scenario collection against a chosen revision, create a new experiment. Keep readers for supported legacy schemas, and reject unknown schemas rather than guessing.

Do not re-record the committed numerical baseline merely because revision directories exist. Establish unchanged legacy behavior with the documented baseline check against a dedicated regenerated comparison tree when implementation touches numerical paths; use WF1 `--notemp`. New revision tests use their own fixtures and outputs.

## Alternatives

**Edit the existing WF1 model and recalculate beside it.** Lowest disk cost and smallest rule change; useful for disposable exploration with no need to keep decisions or rerun old experiments. Rejected for this feature because the last result and current model can diverge, WF1 rebuilds overwrite edits, and old experiment guards can only refuse reruns after the original bytes are lost.

**Recipe-only revisions.** Gives executable provenance and can avoid storing manual binary transformations. Prefer it in a controlled production service where every update is representable by validated recipes. It does not satisfy the confirmed requirement for direct edits, and would mistake “replayable recipe” for guaranteed replay when upstream datasets are mutable. The proposed design records the stronger property where available without excluding snapshot-based expert work.

**Store only patches or overlays on a shared parent.** Reduces storage, especially for forcing and staticmaps, and is preferable if large ensembles of parameter variants dominate cost and a mature copy-on-write object store is already available. Rejected for v1: arbitrary NetCDF edits, file deletions, ancillary HydroMT files and platform link behavior complicate complete reconstruction. Independent full model directories make the runnable boundary inspectable.

**Run evaluations directly against sealed models with external outputs.** Avoids a temporary full copy and is a good later optimization after all Wflow and HydroMT path semantics are proven read-only. V1 uses an isolated copy because current WF1 assumes writable `run_default/` and evaluation paths below its model root. The copy's storage cost is bounded to active evaluations and can be measured before optimization.

**Replace WF1 wholesale with an immutable revision pipeline.** Gives one lifecycle and eliminates the mutable legacy branch. Prefer it for a new project with no baseline or migration obligations. Rejected now because it expands the change into default output paths, archive semantics and every WF1 consumer. Explicit opt-in preserves a small compatibility boundary while the revision path matures.

**A mutable project-wide “selected revision” registry.** Convenient for an interactive UI; preferable when several clients need a transactional preference service. V1 uses the workflow config as the single preference source and freezes selection in each experiment. A second registry would need precedence and race rules without adding scientific information.

## Consequences and remaining decisions

Observable benefits: every revision has recoverable model bytes; manual non-runtime edits are detectable; completed evaluations survive later edits; and a WF1 rebuild cannot change a revision-mode experiment. Observable costs: each revision stores a complete model including forcing; active evaluations need another temporary copy; full integrity checks read the whole inventory; legacy and revision-mode experiment readers coexist.

The design assumes filesystem primitives can provide no-replace publication and exclusive ownership on supported local storage. It does not claim safety against an external privileged process deliberately mutating files during execution. Whole-tree before/after checks expose persistent drift; immutable staging prevents publication of a moving source. Operational instructions require editors and writers to stop before seal.

Decisions needing review before acceptance:

- Confirm the opt-in compatibility boundary, retained native CSV policy and evaluation-copy disk cost.
- Confirm the proposed selection requirement: successful structural/runtime evaluation plus recorded assessor limitations, without a universal fit threshold.
- Confirm the successor simulation-intent schema with an unchanged runtime digest and separate revision binding; assess all v2 readers before implementation.
- Confirm local-storage support and behavior under a managed project root. No claim authority or conformance adapter is assumed to exist.

Implementation probes must establish pinned HydroMT update output completeness, Wflow destination confinement in the evaluation copy, and all WF4 model-root consumers. Failures narrow the supported surface or require a revised design; they are not grounds to weaken the seal.

## Validation and acceptance criteria

These are proposed checks, not results. This drafting stage performed source inspection only; no hydrological execution or test suite was run.

| Claim | Falsifier and required evidence | Owner / gate |
|---|---|---|
| Parent and sealed bytes survive both update routes | Apply a representative native recipe and direct TOML/NetCDF/geometry edits; parent inventory remains identical; child changes are all listed; load child with pinned HydroMT and smoke-run Wflow | model-builder; model-validator accepts before integration |
| Manual provenance is complete | Add, delete and edit files outside TOML pointers; full seal changes while runtime digest can stay equal; unacknowledged edits refuse seal | python-engineer; cst-architect |
| Reader/writer ordering is real | Multi-core fixture delays the last HydroMT writer; no inventory/reader starts early; hold WF1 lock and attempt import concurrently, which must refuse/wait without copying | python-engineer; cst-architect |
| Publication is atomic and non-destructive | Kill before/after seal and publication; race two publishers for one ID; force/fail evaluation jobs; readers see either no object or one complete valid object; previously published bytes survive | python-engineer; cst-architect |
| Evaluation is isolated and attributable | Execute a rapid historical evaluation; compare source inventories before/after; validate effective TOML diff, native responses, export precision and final inventory; inject observation/period/mask/code changes and require a new evaluation ID | model-builder + model-validator |
| Comparison does not confound evidence | Same-protocol pair groups together; altered forcing, station mapping, observation mask or period does not receive an unqualified improvement label; insufficient data is reported explicitly | model-validator |
| WF4 uses the resolved revision everywhere | Two revisions with distinct grid/parameter fixtures: downscaling, resource probing and native run all consume selected root; switch preference after experiment creation and verify existing binding is preserved or explicit disagreement rejected | python-engineer + model-validator |
| Old references cannot be refreshed into compliance | Existing simulation/v2 remains byte-identical; mutate legacy runtime input and require refusal; mutate sealed provenance and require revision-mode refusal even with equal runtime digest | python-engineer |
| WF1 reruns cannot erase revisions | Rerun WF1 on legacy root after import; sealed model, evaluation and experiment inventories remain identical | model-builder; model-validator |
| Recovery and export retain exact attribution | Restore from verified backup; separately import corrupted bytes as new provenance; validate bundle after moving project location; no old manifest is rewritten | python-engineer; cst-architect |
