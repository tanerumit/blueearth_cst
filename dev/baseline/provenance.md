# Baseline provenance

`manifest.json` records WHAT the baseline is. This file records **where it came
from and how far to trust it** — the producing commit, the environment, and a
byte-exact hash of every data target, including the two the manifest does not
hash at all.

It exists because the fixture it describes is **untracked**. `manifest.json`'s
`project_dir` is relative (`test_case/test_local`), so `check_baseline.py`
always fingerprints whichever copy sits under the checkout it runs from. Each
worktree holds its own copy, and within a worktree that copy survives branch
switches — so a pass reports on the tree that last ran there, not on the branch.
Regenerate the fixture and its pre-change state is gone; it was never in git.
The hashes below are.

**Newest section first.** One section per baseline recording; append, never
rewrite. Run `check_baseline.py` from the primary checkout only — a lane's copy
is a seeded snapshot of unknown vintage.

### Where this record is stronger than the gate

The manifest hashes only two of the four. The other two are compared against a
stored reference table with a per-group tolerance, so **a sub-tolerance move
passes the gate and still changes the file**:

| target | gate comparator | manifest carries a sha256? |
| --- | --- | --- |
| `cmip6_change_factors_annual.csv` | normalized sha256, byte-exact | yes |
| `cmip6_change_factors_monthly.csv` | normalized sha256, byte-exact | yes |
| `q_indicators.csv` | `indicator_ref/74ed83c06b2e7e6c.csv`, grouped on `(metric, location)`; ATOL(g) = 1e-3 × mean of abs(value_ref) within g, RTOL = 0.01 | **no** |
| `run_default/output.csv` | `discharge_ref/9baa48f90ceaf138.csv`, per timestep; ATOL = 1e-3 × mean(Q_ref), RTOL = 0.01 | **no** |

The tolerances are deliberate and are not a defect — see `check_baseline.py`'s
module docstring for why each exists. But it means "7/7 green" is not "no byte
moved", and for the two tolerance targets this file is the only byte-level
record anywhere.

The three `project_config_*.yml` snapshot targets are **excluded by design**. A
config migration renames and rewrites them, so they are re-recorded rather than
defended — the precedent is R13's, where *"the split moved the two narrow config
snapshots, the hoist moved all three, and zero data targets moved in either"*
(`dev/LOG.md`, 2026-08-22). They are hashed in `manifest.json` already and need
no second home here.

### Why the 2026-08-25 green is a real verdict

Run from the primary on 2026-08-25, `check_baseline.py check` reported
verbatim:

```
WARNING: manifest recorded by HEAD@0d256a415fe8, checking from main@77e494b3aecd.
         The baseline fixture is untracked and therefore SHARED BY EVERY BRANCH, so a pass here may mean the tree matches another branch's code.
OK - 7 target(s) match manifest.
```

That warning is discharged for this recording, and **not** by the manifest's own
`recorded_by.dirty`:

- `recorded_by.commit` is `0d256a41`, which `git merge-base --is-ancestor`
  confirms is an ancestor of the primary's HEAD `77e494b3`.
- The primary's tree was clean — `git status --porcelain` empty.
- `git diff 0d256a41 77e494b3 -- blueearth_cst/ *.smk config/ scripts/ test_case/ pixi.toml pixi.lock profiles/`
  is **empty**. Nothing that can produce a number changed between the recording
  point and the checked HEAD; the whole diff is `dev/` records, `.gitignore` and
  `.git-workflow.yml`. This, not the flag, is what makes the pass a statement
  about the branch.
- `main` advanced to `020b2844` later the same day, merging the R14 design
  branch. The claim survives it unchanged: the same run-path diff from
  `0d256a41` to `020b2844` is **also empty**, and outside `dev/` that range
  touches only `.gitignore` and `.git-workflow.yml`. The gate was run at
  `77e494b3`; nothing between there and `020b2844` can move a number.
- Independently: recomputing the normalized hashes of both CMIP6 CSVs
  reproduces the manifest's recorded values exactly, and `q_indicators.csv`'s
  raw `63120f16…` matches the determinism fingerprint recorded across three
  post-2.0.0 runs at different core counts.

`recorded_by.dirty` reads `false` here and happens to be correct, but **do not
rest on it**: `record` writes its sidecar reference tables *before* calling
`git_provenance()`, so any re-record whose values moved self-reports dirty —
the flag fails exactly when it would matter. Boarded as `t2608221010`.

That last observation is the one worth having. This file warns that
`q_indicators.csv` and `run_default/output.csv` are compared against tolerance
tables and carry no sha256 anywhere, so a sub-tolerance move passes the gate and
still changes the file. Here it did not: the tables are content-addressed, so an
unchanged filename IS a byte-level statement, and R14's result is therefore
"nothing moved" rather than "nothing moved by more than the tolerance".

The re-record touched five lines of `manifest.json`: the recording branch and
commit, and the three config snapshot hashes.

**One caveat that applies to every pass, not just this one.** `check` warns that
the fixture is untracked and shared by every branch, so a pass can in principle
reflect another branch's code. Here the tree was rebuilt from this branch in the
same session, immediately before the check.
