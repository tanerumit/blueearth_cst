## Findings

### ext1-1 [major]
- section: Uncertainty treatment
- finding: The design's own asymptotic location-information argument is applied only to the ρ=.5 relative gate at n=18, but the identical arithmetic applies to the unchanged **baseline** lower gate and shows that a large, identifiable sub-block of the 144-cell matrix carries thresholds below what a regular estimator can reach even with nuisance parameters known. The design neither states this scope nor pre-registers how such failures are to be interpreted.
- rationale: Using the design's own result (Gumbel per-observation location information 1/σ², P90|μ̂−μ| ≈ 1.645σ/√n with σ and c known): .520σ at n=10, .388σ at n=18, .300σ at n=30, .212σ at n=60. The baseline p=.5 gate is P90(|eσ|) ≤ .25 (confirmed in `criteria.json`: `p90_abs_scale_max {"0.5": 0.25}`), so 9 of the 12 baseline p=.5 cells (n=10,18,30 × three shapes) sit below the known-nuisance asymptotic reference. The ρ=.5 relative gate implies ≤.125σ (design's own e_relative=eσ/ρ derivation, which I checked and which follows from q=ρ when σ_generating=1), which is below the reference at **all four** counts including n=60. Predecessor B's reported n=18 lower P90 range (.484–.558) is consistent with this. Consequence: Stage 3 will sign a handoff recording broad failure in cells whose outcome is largely determined by criterion severity at that n rather than by the L-moment principle, and a reader of that handoff can reasonably but wrongly conclude the candidate estimation principle was tested and rejected. Execution cost is also incurred for cells whose outcome is substantially predictable in advance. This is an asymptotic efficiency reference, not a finite-sample impossibility bound — which is exactly why it belongs in the design as pre-registered interpretation rather than as a criterion change.
- suggested_fix: Without altering any gate, add a pre-registered table of 1.645σ/√n per count against each gate threshold (baseline upper/lower, and the ρ-implied relative thresholds), mark which cells have thresholds below that reference, and state the interpretation rule that failure in those cells is attributed to threshold severity at that n and is not evidence about the candidate. Carry the same table into the Stage 3 handoff.

### ext1-2 [major]
- section: Method
- finding: Step 4 refuses "estimator exceptions" without enumerating them, while the pinned library signals non-convergence with a bare `Exception`, forcing a broad catch that would also absorb environment and infrastructure faults and silently record them as statistical refusals.
- rationale: The cited `lmoments3/distr.html` source raises `ValueError("L-Moments Invalid")` for `lmom_ratios[1] <= 0 or abs(T3) >= 1`, but raises a plain `Exception("Iteration has not converged")` when the Newton branch exhausts `maxit`. A bare `Exception` cannot be caught narrowly, so any conforming implementation of step 4 catches `Exception`, which also captures `MemoryError`-class faults, import/BLAS errors, and array-shape bugs in the adapter. Those would be written into the record as refusals and counted in the denominator of the primary `valid rate ≥.95 over all 1,000 draws` gate. Stage 2's stop rule ("corrupted input, coverage or control failure") does not detect this, because coverage would be complete and every fit would carry a well-formed refusal reason. Consequence: a partially broken run can produce a complete-looking 132,000-fit matrix with a depressed but non-stopping valid rate, and Stage 3 has no recorded basis to distinguish estimator refusal from run failure.
- suggested_fix: Enumerate the refusable set explicitly — the design's own pre-checks, `ValueError` from `lmom_ratios`/`lmom_fit`, and the library's non-convergence `Exception` matched by originating module and message — and require every other exception to propagate and stop the run. Record the exception type, module and verbatim message on each exception-derived refusal so Stage 3 can audit the classification, and report the count of exception-derived refusals separately from domain refusals.

### ext1-3 [major]
- section: Validation regime
- finding: The analytical parameter-recovery control at c={−.2,0,.2} exercises only one of the four disclosed solver branches, and the separate "branch/exception controls" requirement specifies no inputs, no reference oracle and no tolerance. The stated 1e−5 shape tolerance is asserted without reference to the accuracy of the rational approximation it is meant to check.
- rationale: From τ₃=2(1−3⁻ᶜ)/(1−2⁻ᶜ)−3, the three generating shapes give τ₃ ≈ .3048 (c=−.2), .1699 (c=0), .0477 (c=.2) — all strictly positive, so all three controls take the `T3 > 0` branch (`Z = 1 - T3`), with c=0 additionally exercising the `|G| < SMALL` Gumbel snap. τ₃ ≤ 0 requires c ≳ 0.28, well outside the generating shapes, so the `−.8 ≤ T3 ≤ 0` rational branch, the `T3 < −.8` Newton branch and the `T3 ≤ −.97` starting value are reached only through sampling variability — which at n=10 will route some fraction of the 132,000 production fits into code paths that the stated analytical control never checks against an independent computation. Because the design correctly forbids substituting a different root solver, an error or accuracy loss in those branches would be invisible. Separately, the source page discloses no accuracy statement for the rational approximation, so if its error exceeds 1e−5 absolute in shape the Stage 1 stop rule ("ambiguous source behavior") fires on a non-defect, or invites an unauthorized mid-flight tolerance change. Consequence: Stage 3's obligation to independently recompute is unsatisfiable for the branches actually used, and Stage 1 may halt or drift on a tolerance with no stated basis.
- suggested_fix: Enumerate control τ₃ values covering each disclosed branch (for example ≈.50, .1699, .0477, −.30, −.85, −.98), use an independent high-precision root solve of τ₃(c) as the oracle rather than the library itself, and state a per-branch tolerance justified against that oracle. Require the run to emit a branch-usage histogram over all 132,000 fits so Stage 3 can confirm that every branch actually used was controlled; where the library-versus-oracle discrepancy is a property of the approximation rather than a defect, record it as a characterization output instead of a pass/fail control.

### ext1-4 [major]
- section: Validation regime
- finding: The paired A/B, A/candidate and B/candidate comparisons depend on predecessor draw-level artifacts that the design never names, hashes, or confirms carry the required join keys.
- rationale: The design specifies joining "on each pair's intersection of accepted keys: generating shape, count, retained draw ID, probability, and baseline/translated case (including ρ)", and requires both-accepted / first-only / second-only / both-refused counts per cell. The Inputs section pins only `criteria.json` byte-exact plus a generic "input/criteria hashes must be frozen". By filename listing I confirmed that predecessor row artifacts exist but under two different conventions and formats — `draws-c{i}-n{n}-{chunk}.jsonl.gz` plus `samples-c{i}-n{n}.npy` under `.../evidence/gf15/results/`, and `fits-c{i}-n{n}-{chunk}.jsonl.gz` with companion per-chunk `.json` under `.../evidence/gf15-normalized-qualification/results/`. I did not open them, so whether A's rows carry a translated-case/ρ key and a stable retained-draw ID at all is exactly what the design leaves unestablished. Consequence: a Stage 2 deliverable that is a named gate output may be unproducible, or worse, silently computed on a mis-joined or partial cohort whose denominators the design elsewhere takes great care to expose. The same omission applies to the stored fixtures, where "Reuse all original retained draws … do not redraw" is only well-defined once the `.npy` files are named and pinned.
- suggested_fix: Name the exact predecessor fixture and row artifacts with their digests, add them to the frozen input set, document the schema field supplying each join key for both A and B, and make key-coverage verification (all five keys present and complete for both predecessors) a Stage 1 readiness gate with an explicit stop rule. State whether regeneration from the documented `SeedSequence([20260912, shape_index, count])` recipe is permitted, and if so only as a bit-exact equality check against the stored arrays.

### ext1-5 [major]
- section: Uncertainty treatment
- finding: The handoff is required to include a Monte Carlo uncertainty statement, while the same section forbids computing any numerical Monte Carlo uncertainty within this scope, making the required statement necessarily content-free at precisely the point where it matters.
- rationale: The design states that empirical medians, P90s and valid rates "retain unquantified finite Monte Carlo uncertainty", that "Any later uncertainty intervals or replication require separate authorization", and separately that "The handoff must include the Monte Carlo uncertainty statement below". It also acknowledges that reusing the retained draws makes candidate selection adaptive. The gate is a conjunction over 144 cells and three statistics each, with Stage 3's rule that "any criterion failure leaves candidate failed"; a single cell whose P90 estimate sits marginally on either side of its threshold therefore determines the whole verdict, and neither the executor nor the validator is permitted to compute anything that would reveal that the cell is marginal. Consequence: a signed scientific verdict — pass or fail — whose reproducibility on fresh seeds is unknown and, by construction, unknowable from the artifacts, on a candidate the design itself flags as adaptively selected.
- suggested_fix: Authorize a strictly non-gating, per-cell Monte Carlo diagnostic — for example a bootstrap standard error over the 1,000 retained draws for each gated median, P90 and valid rate — reported alongside the deterministic gate outcome, explicitly excluded from gate arithmetic and explicitly incapable of waiving a threshold (consistent with the existing "interval overlap cannot waive a threshold" rule). Require the handoff to flag which cells fall within one diagnostic standard error of their threshold.

### ext1-6 [minor]
- section: Method
- finding: D2's "Baseline fit acceptance is shared across its two requested quantiles" contradicts step 5's per-probability refusal triggers, leaving the disposition of a single-probability quantile refusal undefined.
- rationale: Step 5 refuses on "p outside (0,1), nonfinite intermediate/returned quantiles", which are per-p conditions, but D2 makes baseline acceptance a single shared attribute across p=.9 and p=.5. It is therefore undefined whether a nonfinite quantile at one probability invalidates the shared baseline record — changing the valid-rate denominator of the other probability's cell — or only its own quantile row. The same ambiguity propagates into the translated-pair "unchanged acceptance" comparison. The branch is close to unreachable in practice given the prior c>−1 and σᵧ>0 refusals, which is why this is minor rather than major, but the acceptance semantics are a recorded gate quantity and should not depend on an implementer's choice.
- suggested_fix: State explicitly that quantile-level refusals are recorded per probability and whether they do or do not revoke the shared baseline fit acceptance, and define the corresponding denominator rule for each affected cell.

### ext1-7 [minor]
- section: Method
- finding: D2 records "L-moments" without the normalized/physical distinction it applies to parameters, so the recorded quantities are not the ones step 2's unbiasedness discussion is about.
- rationale: Step 2's unbiasedness statement concerns sample L-moments of the supplied sample. Under the settled range normalization, l₁(y) and l₂(y) are computed from y=(x−a)/s with random a and s and are not unbiased for any fixed distribution's population L-moments; the unbiased quantities are the back-mapped l₁ = a + s·l₁(y) and l₂ = s·l₂(y), recovered exactly by affine equivariance. D2 distinguishes "normalized and physical parameters" and "normalized and physical support membership and log-density" but says only "L-moments". Consequence: a reviewer auditing the design's unbiasedness claim against the record would be checking the normalized quantities, to which the claim does not apply.
- suggested_fix: Record normalized and back-mapped L-moments separately, mirroring the parameter and support treatment, and state in step 2 that the unbiasedness statement attaches to the back-mapped values.

### ext1-8 [minor]
- section: Validation regime
- finding: The "analytical-versus-SciPy quantiles" control is weaker than the design's own oracle-independence requirement implies, because the SciPy reference implements the same expression as the candidate's primary route.
- rationale: The design requires that "Reviewer checks use independently calculated moments/quantiles rather than the same fitting routine as its own oracle" and lists the SciPy comparison among controls that "must falsify". SciPy's `genextreme` inverse uses the c=0 / c≠0 split with the same `-expm1(c*log(-log q))/c` construction that step 5 mandates, so the comparison is strong against transcription errors and against a parameter-mapping or ξ=−c sign error — which is real value — but has no power against a conceptual error in the quantile relation itself, since both sides would move together. The design's phrasing ("physical-parameter SciPy PPF is an independent diagnostic") overstates the independence.
- suggested_fix: Add a genuinely independent round-trip control — verify that an independently implemented GEV CDF evaluated at each returned q̂ₚ recovers p to a stated tolerance — and restate the SciPy comparison as a parameter-mapping and sign control rather than an independent quantile oracle.

## Evidence and limitations

Independently checked, by reading only: `criteria.json` in full, against which every numerical criterion and coverage count in the design matches (`valid_rate_min` .95, `median_scale_abs_max` .1, `p90_abs_scale_max` {".9":.5, ".5":.25}, `translation_paired_abs_max` 1e−6, `relative_qualified_ratios` [.5,2,10], `median_relative_abs_max` .1, `p90_abs_relative_max` {".9":.5, ".5":.25}, `total_fits` 132000, `total_quantile_rows` 144000, the `quantile_formula`, the PCG64 `SeedSequence` recipe, the `zero_relative` null rule and the linear-quantile summary convention); its `estimator` field does name the xclim predecessor, supporting the design's separate-manifest approach. The PyPI JSON metadata for lmoments3 1.0.8 confirms the version exists (uploaded 2024-10-18) and that the wheel SHA-256 matches the design's digest exactly; `requires_python >=3.8.0`, with numpy and scipy declared without upper bounds — so there is no *declared* conflict with the pinned NumPy 2.4.6 / SciPy 1.18.0, and equally no positive evidence of compatibility. The cited lmoments3 source pages confirm, as the design describes them, the T3>0 / T3≥−.8 / T3≤−.97 branch boundaries, `SMALL=1e-5`, `eps=1e-6`, `maxit=20` with `for _IT in range(1, maxit)` (19 updates), `EU = 0.57721566`, the returned `OrderedDict([("c",…),("loc",…),("scale",…)])`, `ValueError("L-Moments Invalid")` for l₂≤0 or |T3|≥1, the bare `Exception("Iteration has not converged")`, and that `lmom_ratios(data, nmom)` returns l1, l2, t3,… via `scipy.special.comb` unbiased order-statistic weights rather than plotting positions. The cited xclim source confirms the PWM claim (`if method == "PWM" and not hasattr(dist, "lmom_fit"): raise ValueError`). By hand I checked the τ₃(c) relation and its c→0 limit, the σᵧ and μᵧ inversions, z_p and its c=0 limit against the SciPy shape convention and ξ=−c, e_relative=eσ/ρ and the ρ=.5 tightening, the 132,000 / 144,000 / 144 / 120,000 coverage arithmetic, and the design's Gumbel location-information derivation (I=1/σ², 1.645σ/√18=.388σ) — all of which are internally consistent and correctly stated.

Not checked: nothing was executed, installed, imported, fitted or benchmarked, and no numerical result was produced; none of the above establishes runtime behaviour of lmoments3 1.0.8 under NumPy 2.4.6 / SciPy 1.18.0. Per the round-1 clean-room rule I read no prior review, ledger, index, status file or agent note. I did not open either predecessor `scientific-handoff.md`, so the motivation figures (3/24 original, 3/24 and 6/72 for B, 30 translation failures, 70 both-refused pairs, 974 nonfinite log-density fits, B's n=18 P90 spans) are unverified; I relied on them only where the design's internal logic does, and ext1-1 does not depend on them. I did not read `intake.md`, so E1–E9 including the E9 lock claim is unverified. I confirmed predecessor fixture and row artifacts exist by filename only and did not open them, which is the basis of ext1-4 rather than a contradiction of it. Finally, the lmoments3 and xclim pages I read are the projects' rendered "stable" documentation, not URLs pinned to 1.0.8 and the pinned xclim release; this does not weaken the findings above, and it reinforces the design's own position that "stable"-labelled documentation is insufficient provenance and that installed source digests must be frozen at Stage 1.
